## 总原则

1. **先通后强**。第一阶段让每一层基建都有最小可用的实现，并接进真实链路；第二阶段起才加深某一层。不允许某一层做得很深、另一层还是空的。
2. **数据先于智能**。先有统一的事件日志。记忆、节奏引擎、数据分析都从它读，不各自记账。
3. **一切可降级**。没网、没模型、超额度、被安全拦截时，产品照常可用，退回预写台词。
4. **规则写成纯函数并模拟**。成长规则（pet.js）已经这样做了；节奏引擎、额度判断也照此，用 60 天模拟验证。
5. **红线有测试**。改提示词、换模型、改上下文装配，都必须跑红线评测，分数不得低于基线。

## 目标架构

```
┌──────────── 安卓壳 / 网页 ────────────┐
│ 界面 app.js（只管展示和交互）          │
│        │                               │
│ Agent 运行时 src/agent/                 │
│  brain   一次「回合」的管线             │
│  prompts 提示词注册表（带版本和输出格式）│
│  memory  记忆块与整理                   │
│  rhythm  节奏引擎（纯函数）             │
│  guard   红线后检、危机识别             │
│  tools   工具注册表                     │
│  events  事件日志（唯一事实来源）       │
│  platform 平台适配：存储/通知/前后台/版本│
└───────────────│───────────────────────┘
                │ 带登录凭证
┌──────────── 服务端 server/ ───────────┐
│ 账号 · 云存档 · 模型网关（额度/备用模型/审核）│
│ 调用追踪 · 远程配置 · 定时任务（第二阶段）  │
└──────────────────────────────────────┘
```

一次「回合」的管线（M1 实现，之后所有模型调用都走它）：

```
触发（讲述/回答/聊天/回来/整理）
 → 输入侧检查（危机识别命中 → 固定安全流程，不调模型）
 → 装配上下文（人设 + 记忆块 + 最近事件）
 → 按提示词注册表调用（选模型档位、长度上限）
 → 解析并校验输出格式（失败重试 1 次）
 → 红线后检（失败重试 1 次，仍失败用预写台词）
 → 产出：台词 / 建议的动作 / 记忆更新
 → 写事件和调用追踪
```

里程碑按依赖顺序排列，前一个的验收是后一个的前提。

### M0 地基与尺子（3–4 天）

| 编号 | 任务 | 产出 |
|---|---|---|
| M0-1 | 平台适配层：存储、通知（先占位）、切到前台/后台的回调、打开外链、取版本号；网页和安卓两套实现 | `src/agent/platform.js` |
| M0-2 | 事件日志：只追加不修改，每条带类型、时间、目标、版本号；现有 `S.logs` 写迁移函数，旧存档能读 | `src/agent/events.js`，存档升到 v3 |
| M0-3 | 红线评测基线：约 30 条用例，覆盖四条红线、输出格式、长度、危机输入；对当前提示词跑出基线分 | `evals/promptfooconfig.yaml`、`evals/baseline.json` |

### M1 Agent 运行时（5–7 天）

| 编号 | 任务 |
|---|---|
| M1-1 | 提示词注册表：每个提示词有编号、版本、模型档位、长度上限、输出格式说明。现有 6 个调用全部迁入：拆关、回应、回来时的问候、切小、旧壳文字、聊天 |
| M1-2 | `brain.run(任务, 上下文)` 按上面的管线实现；app.js 不再直接调用模型 |
| M1-3 | 红线后检 v1：禁用说法（想你、好想、只有我懂你…）、愧疚句式（你已经 N 天没…）、夸大、超长 |
| M1-4 | 危机识别 v1：输入侧关键词和模式匹配，命中后走固定的安全回复，不经过模型 |
| M1-5 | 调用追踪：本地环形缓冲，记提示词版本、模型、耗时、是否重试、是否降级；设置里加「诊断信息」可导出 |

**验收**：全局搜索 app.js 里没有模型调用；断网、给错密钥、模型返回乱码三种情况下流程都不卡；红线评测不低于基线。

| 编号 | 任务 |

| M2-3 | 云存档：沿用现在的整份 JSON 和「较新的胜出」规则；补「导入存档」 |
| M2-4 | 模型网关：服务端函数校验登录凭证，每人每日额度，主备模型自动切换，记用量；密钥只在服务端 |
| M2-5 | 客户端增加「官方」模型来源：登录就能用，不用自己填密钥；自带密钥保留为高级选项 |

**验收**：新装 → 不填任何东西就能和它对话；换一台手机登录后进度恢复；额度用完时退回预写台词并说明原因。

### M3 记忆 v1（5–7 天）

| 编号 | 任务 |
|---|---|
| M3-1 | 两个记忆块：目标档案（≤300 字：到哪了、反复的卡点、偏好的节奏、说过的承诺），你这个人（≤200 字，跨目标） |
| M3-2 | 更新：每次讲述后用快速模型异步增量改写目标档案，不阻塞界面；长成或放归时更新「你这个人」 |
| M3-3 | 上下文装配改成：人设 + 两个记忆块 + 最近 5 条事件 |
| M3-4 | 「它记得」页：能看、能改、能删单条、能清空 |
| M3-5 | 记忆评测：10 段长日记序列，检查档案记住了关键卡点、没有记入与目标无关的敏感信息 |

**验收**：第 30 次讲述时，回应仍能提到早期的卡点；用户删掉的记忆不再出现在回应里。

### M4 主动触达 v1（6–8 天）——最关键的钩子

| 编号 | 任务 |
|---|---|
| M4-1 | `rhythm.js` 纯函数：输入状态、事件、当前时间、用户设置，输出下一次提醒的时间和类型。规则：约定到期日、快睡着前一天、每天最多 1 条、避开安静时段、连续不理按 1/2/4/7 天退避后停发 |
| M4-2 | 60 天模拟：多种用户节奏下验证上限、退避、停发都成立（仿 sim.js） |
| M4-3 | 提醒文案：每次讲述后顺手预生成下一条并过红线后检；没有模型时用模板 |
| M4-4 | 安卓本地通知：权限申请时机（第一次约好下一小步之后再问，不在启动时问）、通知渠道、精确定时权限 |
| M4-5 | 点通知直接进对应界面（讲述或约定） |
| M4-6 | 设置：提醒开关、安静时段、「只在约定到期时提醒」 |
| M4-7 | 记录发送和打开事件，算打开率 |

**验收**：模拟全部通过；真机锁屏能收到，点开直接进讲述；连续不理会按退避停发，用户自己回来后恢复。

### 第一阶段完成的标志

每一层都有了最小可用的实现并接进真实链路：平台、事件、运行时、账号、网关、记忆、触达、安全、观测、工具。然后用真实目标试用两周，用看板数据决定第二阶段先加深哪一层。

## 第二阶段：加深（按试用数据排序，每项 1–2 周）

| 方向 | 内容 |
|---|---|
| 记忆 | 全部日记的检索（先全文，后向量）；跨目标规律（你通常断几天、什么卡点会让你放弃）；每周回顾 |
| 触达 | 学习你的活跃时段；按打开率调整时机和文案；服务端定时推送；国内安卓厂商通道（或用极光、个推等聚合服务）实现离线触达；**桌面小组件**显示它的状态（醒着、睡着、等你），这是不打扰的常驻触点 |
| 网关 | 按任务分模型（便宜模型做抽取和整理，好模型做对话）；提示词缓存；成本看板和每人成本上限 |
| 评测 | 用模型打分评估「追问是否具体」「回应是否诚实」；线上抽样人工复核 |
| 工具 | 读取材料（书的目录、仓库的待办），让拆关和追问更具体；切小步时参考材料 |
| 伙伴 | 栖地里的老伙伴可以回忆聊天（只谈那个目标的过去） |

## 第三阶段：增强（更像一个 Agent）

- **主动规划**：每周主动给出下周的几个小步；发现同一卡点反复出现时主动换策略（换切法、换时间、建议降低标准）。
- **多目标**：同时养几只，它们之间帮你分配时间，而不是互相争宠。
- **更多感官**：语音讲述（说一句话代替打字）、它的声音。
- **商业化**：订阅或按只解锁；额度与付费挂钩。

## 给 Codex 的执行约定

- 一个里程碑一个分支，任务编号写进提交信息（例如 `M1-2 brain.run 管线`）。
- 每个任务完成时：CI 全绿；动到提示词或上下文的跑一遍红线评测并附分数；更新 `docs/design-notes.md` 对应段落。
- 新增的规则类逻辑（节奏、额度）必须是纯函数，并带模拟脚本。
- 不删任何降级路径。没有模型时的预写台词与新功能同步补齐。

## 需要你拍板

1. **安卓壳用的是什么**（Capacitor、原生 WebView，还是别的）？这决定 M0-1 和 M4-4 的写法。
2. **后端放哪**：Supabase 搭建最快，但服务器在境外；国内云（腾讯云开发、阿里云函数计算加数据库）访问更快，合规也更简单，个人信息出境有额外要求。建议：三个月内要面向国内公开上线，就直接选国内云；只是小范围试用，就先用 Supabase，接口抽象好，以后再迁。
3. **官方模型谁付钱**：由你提供（每人每日额度，之后与付费挂钩），还是只支持用户自带密钥。建议由你提供：普通用户不会去申请 API 密钥。
4. **危机时通知紧急联系人**：法规对严重情况有这方面的要求，但它涉及收集联系人信息和误报风险，需要你决定做到哪一步。
